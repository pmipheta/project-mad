## ค่า sample rate ที่แนะนำ (ให้ฝั่ง sampling ใช้)

ความสัมพันธ์ของจอ: 240 samples วาดเต็มความกว้าง 320 px = 5.5 ช่องกริด (ช่องละ 40 px)

```
T/div = N_SAMPLES / (fs × 5.5) = 43.6 / fs   (วินาที/ช่อง)
```

| fs | หน้าต่างเวลา (240 ตัวอย่าง) | T/div ที่ได้ | ใช้ดูอะไรได้ |
|---|---|---|---|
| **100 kSa/s (แนะนำเริ่มต้น)** | 2.4 ms | ~436 µs/div → ปัดป้ายเป็น 0.5 ms/div | sine 1 kHz ได้ ~2.4 คาบเต็มจอ |
| 500 kSa/s | 480 µs | ~87 µs/div | sine 10 kHz ได้ ~4.8 คาบ |
| 2.5 MSa/s | 96 µs | ~17 µs/div | ทางไปสู่เป้า "500 kHz scope" (5 pts/cycle) |

**ทำไม 100 kSa/s:** F767 ADC (12-bit) วิ่งได้ถึง ~2.4 MSa/s ต่อ ADC ตัวเดียว → 100 kSa/s เหลือ headroom ~24 เท่า ตั้งด้วย TIM TRGO + DMA circular 240×2 (ping-pong) ได้สบาย และ Nyquist = 50 kHz ซึ่งพอสำหรับทดสอบด้วย GY-9833 (AD9833) ที่ตั้ง sine 1–20 kHz

**ข้อควรทำ:** อย่าฮาร์ดโค้ดป้าย T/div ให้คำนวณจาก fs จริงเสมอ เช่น
`tdiv_us = 1e6 * N_SAMPLES / (fs * 5.5)` แล้วค่อยเลือกป้ายที่ใกล้ที่สุด — ไม่งั้นป้ายบนจอจะโกหกผู้ใช้

**ทางไป 500 kHz (ถ้าทีมจะอ้างสเปกนั้นจริง):** ต้อง 3-ADC interleaved ให้ได้ ≥ 2.5 MSa/s แล้ว T/div จะเป็นหลัก 10–20 µs/div

## คาดว่า FPS ที่ควรเห็น และถ้าไม่ได้ตามนั้นทำอะไร

ตัวเลขจากการจำลองอัลกอริทึมนี้บนเฟรมจริง (320×240, SPI5 = 24 Mbit/s ตาม `.ioc`):

- waveform frame หนึ่งครั้งเขียน **~1,176 พิกเซล** (ลบเฟรมเก่า + วาดเฟรมใหม่ + grid ที่ถูกทับ) = **~17.6 KB**
- เวลา SPI เปล่า ๆ = **~5.9 ms/เฟรม** → เหลือ budget ในกรอบ 33 ms ค่อนข้างมาก
- รวม overhead ของ HAL/GPIO ต่อพิกเซล (แต่ละ `ILI9341_Draw_Pixel` = 9 SPI transaction) คาดว่าจริงอยู่ราว **10–18 ms/เฟรม → ~25–30 fps**

ถ้าเลข fps บนจอ **ต่ำกว่า ~20** ตัวที่กินเวลาไม่ใช่ SPI แต่เป็น *per-pixel addressing*:
ทางแก้คือเขียนเป็น burst ต่อช่วงแนวนอน (ตั้ง address window ครั้งเดียวต่อ segment แล้วยิงสีรวด) แทนเรียก `ILI9341_Draw_Pixel()` ทีละจุด
